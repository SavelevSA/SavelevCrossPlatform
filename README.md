# Система автоматического контроля лабораторного стенда

Учебное ASP.NET Core Web API на .NET 10. Данные хранятся в SQL Server LocalDB через Entity Framework Core и сохраняются после перезапуска. Подключение устроено по тому же принципу, что в проекте `MvcMovie`, но используется отдельная база `SavelevCrossPlatformLab`.

## Запуск

```powershell
dotnet run --launch-profile http
```

Адрес API при запуске проекта и релизной сборки: `http://localhost:5000`. Порт задан в `appsettings.json` и профиле запуска `http`. В режиме разработки описание OpenAPI доступно по адресу `http://localhost:5000/openapi/v1.json`. Готовые запросы находятся в `SavelevCrossPlatform.http`; полная коллекция для Postman — в `postman/SavelevCrossPlatform.postman_collection.json`.

Для запуска нужны .NET 10 и установленный SQL Server LocalDB (`MSSQLLocalDB`). Строка подключения находится в `appsettings.json` и при необходимости может быть изменена. При первом запуске приложение автоматически применяет миграции из папки `Migrations` и добавляет два примера каждого справочника. При следующих запусках существующие данные сохраняются. База `MvcMovieContext` при этом не меняется.

Обращения к базе данных выполняются асинхронными методами Entity Framework Core (`ToListAsync`, `FirstOrDefaultAsync`, `AnyAsync`, `SaveChangesAsync`). Контроллеры передают в них токен отмены HTTP-запроса. Методы, возвращающие коллекции, используют `List<T>`. Маршруты и формат ответов API остались прежними.

Контроллеры получают через конструктор сервис своего ресурса (`TeacherService`, `LabWorkService`, `ClassroomService`, `ReportService` или `QueryService`) и не обращаются к Entity Framework Core напрямую. Сервисы получают `LabDbContext` и выполняют запросы к базе. Контекст и сервисы зарегистрированы в `Program.cs` с областью жизни одного HTTP-запроса. Бизнес-правила проверки стенда остаются в классах модели.

## Вход и авторизация

Отправьте логин и пароль в `POST /api/auth/login`:

```json
{
  "username": "student",
  "password": "123"
}
```

Как в [примере](https://github.com/Bedvedmalu/CrossPlatformDev), учебный вход проверяет пароль из настроек и определяет роль по логину:

| Логин | Пароль | Роль |
| --- | --- | --- |
| `student` | `123` | `User` |
| `admin` | `123` | `Admin` |

Пользователи и пароли не хранятся в БД. Любой непустой логин с правильным паролем получает роль `User`; логин `admin` получает роль `Admin`. Общий демонстрационный пароль указан в `DemoAccounts:Password` файла `appsettings.json` и может быть переопределён переменной окружения `DemoAccounts__Password`. Неверный пароль возвращает `401 Unauthorized`. Успешный ответ содержит JWT, роль и время окончания действия токена.

Токены действуют два часа. Параметры подписи находятся в секции `Jwt` файла `appsettings.json`; при замене ключа старые токены перестанут работать.

Токен передаётся заголовком `Authorization: Bearer <token>`. Правила доступа:

| Действие | Право |
| --- | --- |
| Чтение преподавателей, работ и аудиторий | Доступно без токена. |
| Чтение отчётов (`/api/reports` и `/api/reports/{id}`) | Любой действующий токен. |
| Все запросы `/api/queries/*`, включая сводку отчётов | Любой действующий токен. |
| `POST`, `PUT`, `DELETE` для четырёх основных ресурсов | Только токен с ролью `Admin`. |

Без токена защищённый запрос получает `401 Unauthorized`. С действующим обычным токеном попытка изменить данные получает `403 Forbidden`. Этот способ входа подходит только для учебной демонстрации: пароль и ключ подписи видны в исходниках. Для настоящего развёртывания нужны отдельные учётные записи с хешированными паролями, секретный ключ вне репозитория и HTTPS.

## Release и демонстрация в Postman

```powershell
dotnet publish -c Release -o release
dotnet release/SavelevCrossPlatform.dll
```

Release-версия также подключается к LocalDB и создаёт таблицы при первом запуске; отдельный файл базы в архив не входит. Импортируйте `postman/SavelevCrossPlatform.postman_collection.json` в Postman и запускайте запросы по порядку. Первые два запроса входят под `student` и `admin` и сохраняют токены в переменные коллекции; третий проверяет `401` при неверном пароле. Далее идут проверки `401` и `403`, CRUD для всех ресурсов, проверка отчёта и три объединённых запроса. Если поменяли пароль через переменную окружения, обновите значения `userPassword` и `adminPassword` в коллекции. Полный прогон коллекции рассчитан на исходные примеры с ID `1` и `2`.

## Предметная модель

| Класс | Данные | Бизнес-метод |
| --- | --- | --- |
| `Teacher` | Имя, дисциплина | `CanSupervise` проверяет, может ли преподаватель вести работу по своей дисциплине. |
| `LabWork` | Название, методические указания, дисциплина, необходимое оборудование, допустимое отклонение | `IsWithinTolerance` проверяет измерение. |
| `Classroom` | Номер и перечень оборудования | `CanHost` проверяет оснащение аудитории. |
| `Report` | Ссылки на три объекта, отклонение, результат, заключение, время | `Recheck` автоматически оценивает три условия и формирует заключение. |

Четыре класса соответствуют указанной теме. При создании отчёта передаётся измеренное отклонение в процентах. Отчёт считается успешным, если профиль преподавателя совпадает с дисциплиной работы, в аудитории есть требуемый прибор и отклонение не превышает допуска. Отрицательное отклонение и значения свыше 100% не принимаются. Созданный отчёт фиксирует результат проверки на момент создания или повторной проверки через `PUT`; изменение справочника само по себе старые отчёты не пересчитывает.

## HTTP API

Для каждого ресурса `api/teachers`, `api/lab-works`, `api/classrooms`, `api/reports` доступны `GET` списка, `GET /{id}`, `POST`, `PUT /{id}` и `DELETE /{id}`. При создании возвращаются `201 Created` и адрес объекта, при обновлении и удалении — `204 No Content`. Несуществующий объект возвращает `404`, некорректный запрос — `400`. Справочник, на который ссылается отчёт, нельзя удалить до удаления отчёта (`409 Conflict`).

Контракты API находятся в папке `DTO`: каждый DTO и преобразователь `DtoMapper` вынесены в отдельный файл. Для каждого ресурса один DTO (`TeacherDto`, `LabWorkDto`, `ClassroomDto`, `ReportDto`) используется как для `POST`/`PUT`, так и для ответов. Его входные поля проверяются атрибутами валидации; ID и вычисляемые поля отчёта заполняет сервер. Для сводных запросов есть DTO с отдельной формой ответа. Сервисы преобразуют сущности базы в DTO перед отправкой клиенту. Поля и адреса запросов Postman не изменились.

Дополнительные запросы с объединением данных и LINQ `Where`/`Select`:

| Запрос | Результат |
| --- | --- |
| `GET /api/queries/report-details?passed=true` | Отчёты вместе с именем преподавателя, названием работы и номером аудитории; фильтр `passed` необязателен. |
| `GET /api/queries/teachers/{teacherId}/works` | Работы, которые может вести преподаватель. |
| `GET /api/queries/classrooms/{classroomId}/works` | Работы, которые можно проводить в аудитории. |

Пример тела `POST /api/reports`:

```json
{
  "teacherId": 1,
  "labWorkId": 1,
  "classroomId": 1,
  "deviationPercent": 2.5
}
```
